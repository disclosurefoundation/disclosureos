# DisclosureOS 2.0.0-beta.4

Current status, checked 2026-10-19: published. All seven packages are available at
`2.0.0-beta.4` under the `beta` tag; stable v1 `latest` tags remain unchanged.
The portal consumes Beta 4. New source additions are not retroactive additions
to this release. See the [Beta 5 integration plan](beta5-integrations.md).

The scope, frozen baseline and preparation checklist below document the candidate
prepared on 2026-10-16. Retain them as the historical release preparation record.

## Scope

This candidate collects the implementation after beta.3 into one reviewed set:

- Records: physical specimens, preparation lineage, custody, laboratory results,
  connected cases, case assessments, supplemental links and shared vocabulary references.
- Schema: supplied-snapshot evaluation, approved public case projections, numerical
  array/CSV/video source selection, rotating and steered radar, cooperative
  secondary radar, active and passive sonar, lidar point clouds, satellite rasters,
  and vocabulary bindings. Portable schemas and readers ship through package exports.
- Observables: revised characteristic definitions, support terms and a full retained
  catalog. A reported characteristic does not establish a claim outcome or origin.
- Origins: full OCS catalog export with hierarchy, qualifications and attribution.
- Scoring: revised vocabulary consumers plus provider-defined policies, numeric
  grades, ordinal levels, exact input/method references and bounded comparison.
  Competing provider results remain separate; there is no universal score.
- Instruments and CLI: advance with their dependencies for a consistent install.
  Existing acquisition, intake and reproducibility workflows remain available.

This includes direct changes to earlier beta observable definitions, support terms
and enriched-observation/scoring consumers. Treat the beta.4 set as one unit;
do not mix beta.3 packages or assume old beta assessments have identical meaning.
The release-closure fix assigns new identities to changed observable and composed
schemas; it does not change the revised scientific definitions.

## Frozen implementation

The implementation baseline is recorded in `beta-plan.json`. Release-mode
verification compares every committed schema against that frozen revision.
A second gate compares identities with the SHA-256 values of published beta.3
schemas, obtained from registry tarballs verified against `dist.integrity`.

The revised observable schema uses `observables/3.0.0/observable-assessments.json`;
the revised composition uses `schema/2.0.0/enriched-observation.json`. Their prior
identifiers retain the previously published bytes. Schema versions are independent
of package versions. No migration or old-definition restoration is required.

The lockfile is refreshed without dependency changes: workspace dependencies stay
`workspace:*` in source and become exact `2.0.0-beta.4` versions in packed artifacts.
No historical hosted schema, release receipt or registry package is overwritten.

## Verification

From a clean checkout at the candidate commit, with Node 22 and the pinned pnpm:

```sh
pnpm install --frozen-lockfile
pnpm test:release
pnpm release:check
pnpm release:pack /absolute/new/beta4-candidate
```

Packages Quality also runs the Node 20 foundation matrix, strict publish checks,
conformance, source-profile reproductions and case consumers. Release-mode packing
checks all seven tarballs, exact internal dependencies, export targets and schema
bytes, then exercises a fresh consumer with NodeNext and Bundler type resolution.
Its manifest records the exact candidate source commit and tarball hashes.

The paired documentation PR must pin that exact commit and exercise the current
17 guide examples with these beta.4 tarballs, including expected failures and
recovery. Its retained receipt is a separate acceptance gate. A source-only
manifest or a reused beta.3 receipt does not satisfy beta.4 verification.

## Historical release preparation checklist (2026-10-16)

1. Review current-head package and documentation CI, the exact candidate manifest
   and guide receipt. Complete remaining browser, accessibility and performance review.
2. When separately authorized, merge the stack in dependency order and verify the
   resulting candidate identity. If package inputs change, regenerate and reverify.
3. Only after publication approval, check registry availability again and publish
   the verified tarballs with `beta`. Confirm all seven registry integrity values,
   fresh installs and unchanged v1 `latest` tags.
4. Then update portal package pins, examples, inspector support, installation
   language and release receipts together, deploy and verify production.

At the time this checklist was prepared, public installation instructions
continued to name beta.3 or their explicitly pinned source candidate until release
verification. Current installation instructions use published Beta 4. Candidate
preparation does not establish independent scientific validity, calibration,
provider identity, external exchange acceptance or access to the native ELDÆON archive.
