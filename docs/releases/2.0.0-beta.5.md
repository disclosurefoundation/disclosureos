## Scope

This coordinated set captures the shared contract work from the ELDÆON, Speculor
and Sky360 integrations:

- Optional MCAP mappings identify the original recording, channel, schema,
  message and selected payload field. Applications can supply their own reader
  without adopting a viewer or reencoding the recording.
- Relative video-frame mappings retain stream identity, presentation-order frame
  and exact rational timestamp without inventing capture UTC.
- Observation 0.2.0 represents an explicitly unknown processing time while
  retaining the processing method, actor and input/output lineage.
- Observation claim history 0.6.0, case record 0.2.0 and case claim history 0.2.0
  support that Observation revision. Offline review requests produce replayable
  receipts. Snapshot checks enforce the declared revision as well as ID and digest.

Records and schema contain the new APIs. Observables, origins, instruments,
scoring and CLI advance with them so all seven packages form one verified set.
Existing published schema identities and bytes remain unchanged. Consumers of
Observation 0.2.0 must narrow the processing-time union before reading a UTC value.

Specialized context, witness, archival and laboratory reviews retain their
Observation 0.1.0 boundary. Public presentation builders retain their existing
case revisions and exact approval requirements. The browser inspector retains
its explicit supported-revision list. See [scope closeout](beta5-scope.md).

## Frozen implementation and artifacts

`docs/releases/beta-plan.json` pins implementation revision
`36cc15418317d5ee6b07cd2d2a64606b1abbc151`, before version preparation.
Schema files must match that commit byte for byte. The published-identity ledger
also checks all retained Beta 3 and Beta 4 identities.

From a clean committed checkout, `pnpm release:pack /absolute/new/candidate`
builds and packs the set, installs the tarballs in an isolated npm consumer and
runs API, schema, example, review replay, migration and TypeScript checks. Its
`release-manifest.json` identifies the candidate source commit and every tarball
by SHA-256. CI retains the manifest and tarballs. A source-mode artifact is not a
substitute for this versioned candidate.

Portal verification must use these artifacts, including transitive dependencies,
and retain its guide, integration and installed-byte receipts. Public portal
package files stayed pinned to Beta 4 during candidate verification. Builds from different
runtimes are separate artifact sets and must carry their own verified manifests.

## Verification and handoff procedure

1. Complete package, conformance, isolated-consumer and portal verification on the
   committed candidate. Review CI and the exact artifact manifest.
2. Obtain separate merge approval. If the merged tree changes package inputs,
   regenerate and reverify the candidate before release.
3. Obtain npm publication approval. Recheck registry availability, publish only
   the approved artifacts under `beta`, verify registry bytes and fresh installs,
   and confirm unchanged stable v1 `latest` tags.
4. Then update portal dependencies, documentation availability and production in
   a separate reviewed change. Git tags and release announcements are separate.

Provider permissions remain separate from package release. ELDÆON original-data
access goes through its restricted licensing page; Speculor reuse approval and
Sky360 media confirmation remain separate checkpoints. No provider recordings
are added to the npm packages. Original-media comparisons are not repeated by
candidate compatibility checks; their retained receipts remain the source record.
