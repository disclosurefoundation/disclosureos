# DisclosureOS 2.0.0-beta.0 candidate

This is a coordinated package candidate for external integration testing, not a
stable standard release or a publication announcement. All seven packages use
`2.0.0-beta.0`; the publication tag is `beta`. Existing npm `latest` versions and
the portal's v1 default remain unchanged until separate publication and portal
handoff steps are completed.

## Scope

| Package | Included in this candidate |
| --- | --- |
| records | Explicit missingness, source assertions, measurement context, experimental observation and attributed claim-history contracts. |
| observables | Existing technology and biologics definitions within the exact beta dependency graph. No new scientific endorsement or v2 assessment API is implied. |
| origins | Existing hypothesis catalog within the beta dependency graph. No new scientific endorsement or v2 origin API is implied. |
| instruments | Existing sensor manifests plus experimental acquisition context and declared instrument/calibration history checks. |
| scoring | Population coverage, experimental assessment summaries and reproducible summary evaluation. Legacy scoring remains separately available. |
| schema | Experimental acquisition/measurement bindings, dataset releases, source intake, research prerequisites, versioned profiles/evaluation, reproduction packets and migration document contracts. |
| cli | Explicit experimental validation/profile commands and the bounded local migration workflow, including review, accounting, application, read selection and rollback. |

The implementation baseline is canonical commit
`ca6cc10854093966fd203228ee502907bb507e1a`. This packaging checkpoint changes
versions, dependency pins, documentation and release tooling; it does not change
observation semantics or schema bytes. The generated artifact manifest names the
actual candidate commit separately from that implementation baseline.

## Version and compatibility decisions

The coordinated `2.0.0-beta.0` version identifies the next standard's test set.
It does not move experimental APIs into root exports. Existing root APIs remain
for compatibility, while v2 workflows require explicit imports:

```ts
import { parseExperimentalObservation } from '@disclosureos/records/experimental/v2';
import { evaluateMeasurementBindings } from '@disclosureos/schema/experimental/v2';
```

The seven packages are versioned together for this beta to make consumer pins
unambiguous. Their internal `workspace:*` references become exact `2.0.0-beta.0`
dependencies when packed by pnpm. Zod is pinned to the validated `4.4.3` across
packages. Use pnpm to pack; raw `npm pack` does not perform pnpm workspace/catalog
substitution and is not the release artifact path.

Legacy HTTPS schema IDs and experimental URN IDs remain unchanged. Package
versions, document schema versions and profile/policy versions are separate.
The manifest inventories every shipped schema by path, ID and digest, and records
exported profile/policy/ruleset identities and vocabulary content. URNs identify
contracts; resolve them using the manifest and package schema exports, not HTTP.
Do not copy experimental schemas over existing hosted v1 URLs.

## Verify before publication

From the canonical repository using Node 22 and pnpm 9.15.0:

```sh
pnpm install --frozen-lockfile
pnpm --filter '@disclosureos/*' build
pnpm --filter '@disclosureos/*' type-check
pnpm --filter '@disclosureos/*' test run
pnpm --filter '@disclosureos/*' lint:publish
node --test conformance/*.test.mjs scripts/audit-partner-window.test.mjs scripts/partner/map-eldaeon-intake.test.mjs
pnpm conformance:baseline
pnpm conformance:matrix
pnpm test:release
pnpm release:check
# Commit all reviewed changes before this command; its output is outside the repo.
pnpm release:pack /tmp/disclosureos-beta-candidate
```

The output directory must not already exist. `release:pack` never publishes.
It retains tarballs, an independent npm consumer and a manifest only marked
`passed` after export resolution, schema equality, TypeScript consumer checks,
the observation/claim corpus and installed-CLI WP09 acceptance all succeed.
Failures exit nonzero and leave diagnostic artifacts without a passing manifest.
The manifest includes the commit, lock hash, runtime, tarball hashes and exact
packed dependencies. Archive this output with the review/release record.

The consumer uses npm with lifecycle scripts disabled; it has no links back to
workspace packages. Type checking covers NodeNext and Bundler resolution. The
existing full conformance suite separately exercises acquisition, evaluation,
datasets and migration. These software checks do not certify scientific claims.

## Publication and portal handoff

After the PR is reviewed and merged, generate and verify the candidate from the
exact release commit. Obtain authorization for npm publication and follow the
[release process](../release-process.md). Check registry availability and `beta`
tags, verify `latest` still points to v1, then pin the exact published versions in
the separately labeled portal beta. Keep v1 documentation available and replace
the private inspector only after parity with its fixtures and acquisition checks.

Do not rerun versioning simply to publish this already-versioned candidate. For
future beta changes, add a changeset, run versioning in the existing prerelease
mode, review the incremented versions and refresh the candidate plan. Stable
publication requires a separate review of prerelease exit, publishing tags,
schema identities, scientific review and governance.

## Remaining boundaries

The ELDÆON native archive, partner mapping approval, independent semantic consumer,
real-data reproduction, qualified scientific review and governance assignments
remain external/stable-release gates. The public ten-minute visualization extract
is not a native acquisition dataset. Python integrity checks and synthetic
reproduction are not substitutes for independent scientific validation.

WP09 remains complete for its supported bounded local workflow. A new source
format or production database migration needs a concrete integration requirement;
this beta does not add another migration subsystem.
